# USD：Pipeline 驗證與 QC 架構

全套架構訂下了數十條「鐵律」、「嚴禁」與「必須」。但**沒有強制執行機制的規範一定會腐化**——USD 的多數違規並不會報錯，只會靜默地產生錯誤結果：材質覆寫寫了沒反應、角色躺倒 90 度、農場帶著未鎖定的版本算完整卷。

本篇規範 Pipeline 的驗證體系：**檢查什麼、在哪個關卡檢查、失敗如何處置**。

---

> [!IMPORTANT]
> **30 秒核心原則**
> 1. **本篇是索引，不是規則本體**：每條檢查僅描述「查什麼、何種級別、何時執行」，規則的定義與理由一律留在其主場文件。**規則永遠只有一份**，避免兩處敘述日久分歧。
> 2. **與 `usdchecker` 職責分工**：`usdchecker` 驗證的是**檔案是否符合 OpenUSD 規範**；本套驗證的是**內容是否符合本 Pipeline 的架構規範**。兩者互補，皆須執行。
> 3. **三級嚴重度**：**攔阻（Blocking）** 中止流程、**報告（Report）** 僅列出供確認、**建議（Advisory）** 提示最佳實踐。並非所有違規都該擋。
> 4. **三道關卡**：**發布前**（Pre-flight）、**送算前**（Pre-render）、**交付前**（Pre-delivery），各自檢查不同項目。
> 5. **靜默失敗是本體系的首要敵人**：多數檢查針對的是 USD 不會報錯、畫面卻已錯誤的情境。驗證工具的價值正在於把這些錯誤提前到發布關口。
> 6. **豁免必須具名、具時限、具追蹤**：外包交付與歷史遺留 Asset 無法一律擋到修好，但豁免不得成為常規通道。

## 1. 定位：索引而非規則

### 1. 為什麼不在本篇重述規則

每條檢查的「為什麼」都牽涉完整的架構推論——例如「幾何零綁定」背後是「descendant direct binding 恆強於 ancestor 繼承意見，與圖層強弱無關」這整套 LIVRPS 分析。若在本篇重寫一次，兩份敘述遲早分歧，屆時沒有人知道哪一份才算數。

因此本篇的每條檢查只回答三個問題：

| 欄位 | 內容 |
| :--- | :--- |
| **檢查什麼** | 可程式判定的具體條件 |
| **嚴重度** | 攔阻 / 報告 / 建議 |
| **規範來源** | 連回定義該規則的章節 |

### 2. 與 `usdchecker` 的職責分工

兩者檢查的是**不同層次**的正確性，缺一不可：

| | `usdchecker` | 本 Pipeline 驗證 |
| :--- | :--- | :--- |
| **驗證對象** | 檔案是否符合 OpenUSD 規範 | 內容是否符合本架構規範 |
| **典型項目** | Schema 合法性、檔案格式、貼圖路徑可解析 | `/ROOT` 鐵律、材質綁定契約、Stage Metadata 一致性 |
| **規則來源** | OpenUSD 官方 | 本文件體系 |

> [!TIP]
> **`usdchecker` 應作為前置步驟先跑**
> 檔案層級若已不合規（Schema 錯誤、路徑壞鏈），架構層級的檢查多半也沒有意義。建議流程為：`usdchecker` 通過 → 才執行本套驗證。

## 2. 三級嚴重度

**並非所有違規都該擋。** 過度攔阻會使藝術家繞道而行，反而使驗證失去意義。

| 級別 | 行為 | 適用情境 |
| :--- | :--- | :--- |
| **攔阻（Blocking）** | **中止流程**，清理暫存並報錯 | 違規會導致下游靜默錯誤，且必定需要重工 |
| **報告（Report）** | 列出清單供發布者確認，**不中止** | 「可能是刻意為之」的情形——發布者最清楚意圖 |
| **建議（Advisory）** | 提示，不影響流程 | 最佳實踐偏離，但不影響正確性 |

> [!IMPORTANT]
> **報告級的判準：該行為是否可能是刻意的**
> 最典型的例子是 [`kind` 階層斷裂](usd-asset-layer.md)——一顆 model 掉出 Model Hierarchy 並非格式錯誤，而是**能力喪失**；而 Kitbash Asset 與 `PointInstancer` 原型分支的斷裂**正是所欲的結果**。
>
> 此類檢查若設為攔阻，等同強迫發布者去「修正」他刻意的設計。正確作法是**列出斷點供其確認**，唯有當他已明確聲明需要該能力（例如已為該 Prim 指定 `drawMode`）卻實際失效時，才升級為攔阻。

## 3. 三道關卡

各關卡檢查的範圍不同——愈往後，檢查對象從「單一發布包」擴展至「整棵依賴樹」。

```text
┌── 發布前 (Pre-flight) ──────────────────────────────────┐
│  對象：單一發布包                                        │
│  時機：Staging 完成、原子移轉之前                        │
│  失敗：清理暫存目錄並中止，正式結構 100% 保持純淨        │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌── 送算前 (Pre-render) ──────────────────────────────────┐
│  對象：整顆鏡頭的合成結果與其依賴樹                      │
│  時機：提交農場之前                                      │
│  失敗：拒絕提交                                          │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌── 交付前 (Pre-delivery) ────────────────────────────────┐
│  對象：交付包的完整性與自洽性                            │
│  時機：打包交付客戶或長期封存之前                        │
│  失敗：拒絕打包                                          │
└─────────────────────────────────────────────────────────┘
```

> [!CAUTION]
> **送算前與交付前的檢查，無法由發布前的檢查取代**
> 發布前只看得見**單一發布包**。而「鎖定清單是否遞移涵蓋整棵依賴樹」、「交付包內的 `latest` 是否已解析為具體版次」這類問題，**本質上跨越多個發布單元**，必須在後兩道關卡才驗證得到。詳見 [發布封裝篇](usd-publish-packaging.md)。

## 5. 豁免機制

**一律擋到修好為止並不可行。** 外包交付、第三方 Asset 庫、歷史遺留 Asset 與急件，都會出現「明知不合規但當下無法修正」的情形。若無豁免通道，藝術家終將繞過驗證工具，屆時整套體系形同虛設。

但豁免亦**不得成為常規通道**。故規範如下：

> [!IMPORTANT]
> **豁免必須具名、具時限、具追蹤**
> 1. **具名**：記錄核准人與申請理由，**嚴禁匿名豁免**。
> 2. **具時限**：每筆豁免皆須設定失效日期；逾期未整改即自動升級為攔阻。
> 3. **具追蹤**：豁免記錄寫入 Asset 管理系統，並隨該發布單元一同追溯。
> 4. **範圍最小化**：豁免僅對「特定發布單元的特定檢查項」生效，**嚴禁全域關閉某項檢查**。
> 5. **報告級不適用**：報告級本就不中止流程，無須亦不得申請豁免。

> [!WARNING]
> **定期審視未結案豁免**
> 豁免清單若只進不出，最終會累積成一份無人知曉的技術債，且新人會誤以為那些違規是可接受的常態。應定期（如每個里程碑）審視未結案豁免，逐筆確認仍有必要或推動整改。
>
> 此原則與 [Collection-Based Binding 的例外機制](usd-asset-layer.md)一致：**每次動用都代表有一顆 Asset 未達發布標準**，應同時標記待整改，而非讓例外淪為繞過鐵律的常規手段。

## 6. 工具鏈與 CI 整合

### 1. 三層防禦

沿用 [Implicit Layer 治理](usd-solaris-implicit-layer.md)已確立的防禦模型，全體檢查項一體適用：

| 防線 | 執行位置 | 目的 |
| :--- | :--- | :--- |
| **第一防線：源頭治理** | DCC 內的製作規範與範本 | 從一開始就不產生違規內容 |
| **第二防線：發布前檢核面板** | 藝術家按下發布之前 | 在他自己的環境中提早預警，成本最低 |
| **第三防線：發布流程攔截** | Staging 完成、原子移轉之前 | 最後守門，違規即中止並清理暫存 |

> [!TIP]
> **第二防線的價值最高**
> 走到第三防線才攔下，藝術家已經花費了完整的輸出時間，且需重新走一次流程。**檢核面板應與發布工具共用同一套規則實作**，確保「面板上通過」與「發布時通過」永遠一致——兩者若各有一套判斷，反而製造新的困惑。

### 2. 規則以模組形式註冊

各檢查項應實作為**獨立、可單獨啟用的規則模組**，而非一支巨大的驗證腳本：

- 新增規範時只需新增規則模組，不動既有程式。
- 各規則可獨立測試，並以本篇表格中的「判定條件」為測試案例。
- 不同發布類型（Asset、FX Element、鏡頭、Pure USD 單元）可套用不同的規則集合。

> [!NOTE]
> **既有實作**
> [`tools/layerinspector/layer_inspector.py`](../tools/layerinspector/README.md) 已實作 §4.5 的「Implicit Layer 未外溢」與「無壞鏈 Sublayer」兩項，可作為規則模組的實作範例與介面基準。

### 3. CI 整合

本文件體系本身亦應納入驗證——規範與實作分離時，最先腐化的往往是文件內的範例：

| 項目 | 檢查內容 |
| :--- | :--- |
| **文件內 USDA 範例可解析** | 抽取文件中的 `usda` 區塊，確認語法合法 |
| **跨篇錨點連結有效** | 文件間的章節錨點連結皆可解析 |
| **檢查項與規範來源同步** | 本篇表格所引的章節確實存在 |

## 7. Pipeline 規範對照總表

| 維度 | 規範 |
| :--- | :--- |
| **本篇定位** | 索引而非規則本體；規則永遠只有一份，留在其主場文件 |
| **與 `usdchecker` 關係** | 職責互補，`usdchecker` 先跑、本套後跑 |
| **嚴重度** | 攔阻 / 報告 / 建議三級；「可能是刻意為之」者一律列為報告 |
| **關卡** | 發布前、送算前、交付前；後兩者檢查跨發布單元的項目 |
| **豁免** | 具名、具時限、具追蹤、範圍最小化；報告級不適用 |
| **防禦層次** | 源頭治理、發布前檢核面板、發布流程攔截，三者共用同一套規則實作 |
| **實作形式** | 獨立可註冊的規則模組，依發布類型套用不同規則集合 |
